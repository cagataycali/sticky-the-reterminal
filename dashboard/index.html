    Dashboard — sticky.cagatay.my·

    A remote-control cockpit for the Sticky: device status, live screen mirror, a render_ui composer, action buttons and an activity feed — served behind a WebAuthn passkey gate at https://sticky.cagatay.my (Cloudflare Tunnel sticky, backend on localhost:8787).

    Code lives in docs/dashboard/: FastAPI backend (server.py) + React/Vite SPA (frontend/), launched by run.sh.

    How it controls the device·

    The Sticky is not on a LAN socket — it's controlled through the tiny.technology device relay:

    sequenceDiagram
    participant B as Browser (passkey)
    participant D as Dashboard backend
    participant T as tiny.technology
    participant S as Sticky
    B->>D: POST /api/invoke {command}
    D->>T: POST /api/devices/relay {toDevice, payload:{type:"invoke",prompt}}
    T-->>D: {id: "env_…"}
    S->>T: PUT /api/devices/relay (5s poll)
    T-->>S: envelope
    S->>T: PATCH /api/devices/relay (reply)
    D->>T: GET /api/devices/relay?inReplyTo=env_…
    T-->>D: reply {result, images?}
    D-->>B: result

    Two credentials, two directions:

    • the backend authenticates to tiny.technology as the owner — the same Bearer credential the tiny CLI writes to ~/.tiny/credentials.json (override: TINY_CREDENTIALS)
    • the browser authenticates to the backend with a passkey — WebAuthn (Touch ID / Face ID); the private key never leaves the secure enclave, the backend stores only the public key (.sticky_auth.json, chmod 600)

    The async contract mirrors use_device: an invoke waits up to 45 s, then returns {pending, envelope_id}; GET /api/result/{envelope_id} redeems the reply later (the relay mailbox keeps it ~24 h). Image URLs in replies pass the same plugin.tiny.technology/media/* allowlist the tiny agents apply.

    Live mode — the real fridge panel·

    STICKY_MOCK=0 STICKY_DEVICE=sticky ./run.sh          # what runs today

    Live mode is the production mode. The rules it plays by (fw 0.14.18-m12) — every one of them exists because the first live attempt lied on screen:

    thing how live mode handles it
    status reply shape since 0.9.x the firmware answers machine-readable JSON (fw, battery_pct, charging, wifi, ssid, rssi_dbm, heap_free, psram_free, + a human summary field). parse_status() still accepts the older English sentence and reports which shape it saw; absent fields render as —, never as a guess. GET /api/status is the normalized route.
    screen mirror the screenshot verb uploads the framebuffer and answers with a hosted URL in the reply text (screenshot: https://plugin.tiny.technology/media/…png), not in images[]. The backend extracts it, checks it against is_device_media_url, and proxies the bytes at the guarded /api/screen.png — so the mirror is the REAL panel and the media URL never has to be exposed to the browser.
    clickable mirror the relay cannot read the panel's current card back, so the backend remembers the last card spec it sent and derives button boxes with the firmware's own geometry (800×480, margin 24, 56 px bar at the bottom, gap 16, n≤4 split evenly — pixel-verified against a device screenshot).
    clicking a button a click cannot press the glass. It is logged as sim_tap and labelled "simulated" in the feed and in the UI. Real taps come from the device: the firmware posts them as device_note ui_tap button=N label=…, and the backend reads them owner-side from GET /api/events, showing them as ui_tap (source device). Tap zones whose id/label the firmware itself will act on (the action_for() sniff — m: rows, rescan wifi, …) are badged ⚡ with a dashed outline, and the tooltip says exactly what a real finger would also trigger; report-only zones stay clean. The badge runs the same deviceActionFor mirror as the composer lint — one truth, two surfaces.
    verbs the firmware lacks wake, reprovision, image, stream are refused with HTTP 501 + the reason, and their Action buttons are greyed out with that reason. An action that does nothing is a lie on the screen.
    slow envelopes every relay call runs in a threadpool (run_in_threadpool), so a 60 s pending invoke never freezes the dashboard — and a pending envelope is tracked, not dropped — and since the reaper went autonomous, redemption no longer depends on a browser being open: the registry persists to disk on every mutation (a launchd respawn mid-deploy no longer orphans in-flight envelopes), and a startup task polls every 20 s only while envelopes are in flight, blanket-caught so the reaper never dies. A late reply still lands in the feed (marked ↩), a late render_ui still updates the mirror's card truth, a late screenshot still updates the mirror image. After 15 min unanswered it's logged as expired (⌛) — abandoned visibly, never silently. In-flight envelopes are surfaced in /api/activity and as a banner. The original design redeemed only on activity polls — which meant owner out, late replies rot; that gap was found by its own fixtures (chart envelopes orphaned by a respawn) and closed.

    Verbs that actually exist (fw 0.18.0-m14, nineteen, all advertised): render_ui <card-json>, status, sensors [card], say <text>, ask <text>, voice [secs], screenshot, glance, miccheck [secs], page <nav>, rotate [deg|auto], tap <x> <y>, swipe <x1> <y1> <x2> <y2>, scroll [up|down|top|±px], lock, unlock, sleep [secs], ota [channel], messages [unread|thread <login>] — the verb-by-verb reference is Commands. The four that arrived after this page's original audit (swipe in caps, lock/unlock at 0.17.0, glance at 0.18.0) are exactly the case the next paragraph exists for: the capabilities handshake lights their buttons from the heartbeat, no dashboard deploy required.

    Since the capabilities pass, verb truth comes from the device itself: /api/capabilities crosses the dashboard's static table with the verbs the firmware advertises in its own heartbeat (first verified live at 15 verbs round-trip; the array has since grown to 19 — parity held, see Commands). A verb shipped by OTA lights its button without a dashboard deploy — the Sensors button staying grey for a day was exactly this staleness class. The semantics are honest in both directions: the device's word wins; unadvertised verbs grey out with the reason; verbs the firmware advertises that have no dedicated UI yet get a 🆕 chip pointing at the raw console; and if the platform is unreachable the static table takes over with the footer naming which source is speaking.

    The verb console covers all of them with structured controls, not a free-text box: a nav ring for page (home/status/sensors/settings/wifi/ble + back/prev/next), a rotation control (0/90/180/270/auto/report, with the device's IMU answer read back), miccheck with a live/SILENT verdict badge parsed from the JSON reply, and sleep with timer-wake seconds. The console builds positional prompts for every sscanf-parsed verb — a lesson paid for on real glass: the first say implementation sent JSON and the panel dutifully rendered the literal braces. The screen mirror carries scroll controls (⤒ ▲ ▼) that drive the glass's own scroll verb and read back its pixel receipts (offset/content_h), refreshing the mirror after each step — scrolling the real panel from the browser, with the panel's own numbers as proof.

    Mock mode — the software Sticky·

    STICKY_MOCK=1 (the default) swaps the relay for mock_device.py, which implements the device end of the envelope contract per the API contract — envelope dispatch, sleep-gating, help-on-unknown — and renders card specs to a real 800×480 PNG quantized to the 4 e-ink gray levels. It implements every verb, including the ones the firmware has not shipped, so it is the right target for UI work; a mock click is a real ui_tap because the mock device is the one being clicked.

    Auth lifecycle·

    1. Unclaimed: /auth/status → setup_required. First enrollment is gated by STICKY_AUTH_BOOTSTRAP_TOKEN (the UI asks for it) so a public URL never has an open enrollment window — without the token, register/begin answers 403.
    2. Sealed: every /api/* route requires the session JWT (cookie or Authorization: Bearer); unauthenticated → 401. Additional passkeys can be added from a signed-in session; the last passkey cannot be deleted.
    3. Sessions last 24 h (STICKY_AUTH_TOKEN_TTL). A mid-session expiry is handled as one event: the first 401 on /api with a held token raises a single banner and the login gate — not a wall of failing cards.

    Verified end-to-end with a CDP virtual authenticator (puppeteer + system Chrome): register → seal → invoke → clickable mirror tap → logout → passkey login, plus cookie-less 401/403 checks against the public URL.

    Cards·

    card source
    📟 Device status — fw/battery/wifi/heap/display GET /api/status (both reply shapes), 30 s
    🛰 Fleet row — name/id/kind/online/last seen GET /api/device → platform /api/devices, 60 s
    🪞 Screen mirror — the real frame, clickable POST /api/screenshot → /api/screen.png + /api/buttons
    🎨 render_ui composer — presets + JSON editor + live lint render_ui envelope (card spec v1) — the lint mirrors the firmware dispatch (7 types, keys, buttons≤4, priority), warns without blocking (the glass's receipt is the judge; only JSON parse errors block); presets include a scrollable 24-row list and an alert card. The lint is pinned to a declared grammar (LINT_GRAMMAR=2, stated next to the rules it mirrors), and status polls feed fwGrammar — the device is the only authority on what it speaks. On mismatch the Status card raises a ⚠ drift banner and every lint result confesses which version its rules mirror. The design proved itself the same night it shipped: grammar v2 (the messages dialect) reached the glass within hours of the pin landing, the banner fired unprompted on the first 0.14.11 poll, and the lint was then caught up — v2's real definition (verbs + button-id namespaces like m:, not card types) with the m: rows annotated. The Status row also shows fw_commit, so the panel can prove the deploy's ancestry at a glance
    ⚡ Actions — ask, voice ask, OTA (+greyed-out gaps) GET /api/capabilities decides what is clickable. The ota action carries a direction guard: a fresh status probe captures fw_before, the reply returns ota_guard{fw_before,note}, and staging opens a 30-minute watch: every parsed status receipt feeds the redeem, which logs the verdict itself — ⬆✅ upgraded, ⬆🚨 DOWNGRADED, ⌛ expired-unredeemed — receipts-based, because the channel pointer is device-token-auth'd and direction is provable only by evidence, not intent
    💬 Messages — owner inbox, threads, unread badge, compose GET /api/messages (owner-side poll, 60 s); opening a thread (GET /api/messages/{peer}) is the explicit act that marks it read — and logs itself to the activity feed as dm_open, because a read-marking side effect should leave a trace. Sending is real: POST /api/messages delivers a DM through the owner relay (send_dm) — body capped at 2000 code points and rejected over-length, never truncated; an empty message is refused; the reply reports actual delivery (telegram/push/stored). Every send carries viaTiny provenance: a message composed by an agent or this dashboard must never claim a human typed it. 📟 deep-link buttons push the firmware's messages / messages thread <login> verbs — the same inbox or conversation appears on the physical glass, fetched by the device with its own token
    📜 Activity — envelopes, replies, REAL ui_taps, sim_taps /api/activity ring + platform event ring, 5 s poll — entries render in receipt language (↕ scroll offsets in px, 🎨 committed-to-glass, ↩ late reply, ⌛ expired, ⏳ pending), and a ⬇ export button hands the whole session (receipts + in-flight) to another lane as timestamped JSON

    The Sensors card exists now — but as an on-demand read, never a poll (each real read power-cycles the gyro, and a 30 s poll would spend the 750 mAh pack to decorate a dashboard). /api/sensors passes the firmware's JSON through verbatim — field names measured off tiny_sensors.cpp's emitters, not predicted — and the render is provenance-honest: gyro renders live dps when the read carries values (measured: it does), and a null gyro is explained as powered-down rather than dressed up as an error, absolute mAh appears only when mah_trusted is true, and an untrusted gauge is explained with its own numbers (design 7500 vs pack 750) rather than hidden. The card shows what the device knows and how much the device trusts what it knows.

    The HTTP surface·

    Every route in server.py, so integrators never have to read the cards table sideways. All /api/* routes require the session JWT (cookie or Bearer) except /api/health; /auth/* is the WebAuthn lifecycle.

    route what it does
    GET /api/health unauthenticated liveness: mode (mock/live), device selector, whether first-passkey setup is still required
    GET /api/capabilities the device's own advertised verb list — what the UI is allowed to light up
    GET /api/device fleet row for the selected device via platform /api/devices
    POST /api/invoke raw verb → relay envelope; waits ≤ 45 s then returns {pending, envelope_id} (the use_device contract)
    GET /api/result/{envelope_id} redeem a pending envelope later (relay mailbox keeps ~24 h)
    GET /api/status · GET /api/sensors normalized status (both reply shapes) · firmware sensor JSON passed through verbatim
    POST /api/screenshot → GET /api/screen.png trigger a framebuffer upload, then proxy the allowlisted media URL — the browser never sees it
    GET /api/buttons the tap zones of the last card, with bboxes, for the clickable mirror
    POST /api/tap simulated only, and it says so: refuses ids not on the last card sent from here (404), logs sim_tap with "the device did NOT feel this". Real ui_taps arrive the other way — device → platform event ring → activity feed
    GET /api/messages · GET /api/messages/{peer} · POST /api/messages inbox · thread (marks read, logs dm_open) · real DM send with the viaTiny provenance flag (see the Messages card row)
    GET /api/activity receipt-language feed + in_flight envelopes + upstream events_error when the platform pull is failing
    GET /auth/status · POST /auth/register/begin·finish · POST /auth/login/begin·finish · POST /auth/logout · GET·DELETE /auth/credentials passkey lifecycle — first enrollment gated by STICKY_AUTH_BOOTSTRAP_TOKEN; the last passkey cannot be deleted
    POST /api/dither → GET /frames/{sha16}/{name} image rail: upload any image → dithered, exact-size raw e-ink frames + PNG previews. The GETs are capability URLs — sha16 of the content is the secret, no cookie — because the device fetches them over plain http_request with no cookie jar. GET /api/dither returns the machine-readable contract (lesson learned: without it, the SPA catch-all served index.html and a firmware author would parse a web page as a spec)
    POST /api/frames → GET /api/frames/{seq_id}/{manifest,n.raw,n.png} anim rail (M-A8's backend half): anim-grammar JSON in (EINK_ANIMATION.md §4 — ops blit/rect/card_diff/delay/flush, canvas persists across ops, each paint op emits one frame) → Pillow rasterize → manifest + exact-size frames (0.raw = 48 000 B for 1-bit, receipt-verified) shaped for the firmware's tiny_stream_play(manifest_url, interval_s, max_frames) contract — which today is a header-only declaration (tiny_stream.h, no .cpp): the device half of M-A8 is unbuilt, and this repo has already learned what headers-without-implementation cost (the provisioning portal shipped months after its header did). The rail renders to the written contract precisely so the firmware has something real to test against when its half lands. Caps enforced server-side and re-enforced on device (120 frames / 60 s; refusals carry the arithmetic). POST needs the session; the GETs are capability URLs like the image rail. GET /api/frames = public contract
    GET /api/settings · POST /api/settings/wifi · DELETE /api/settings/wifi/{ssid} · POST /api/settings/toggle remote settings rail (M-A9C) behind an honest capabilities gate: every write answers 409 with the gate sentence until the firmware advertises a config verb — the page never pretends a knob exists that the glass can't turn, and saved networks stay unlisted until config grows a get side (a gate sentence, never a fake list). Wi-Fi credentials ride a redacted invoke path: the password never enters the activity log, only a redacted line does
    GET /s/{device_id} scan-to-configure: the mobile page a QR on the glass points to. The page itself is public-shaped (holds no data); every API call it makes is WebAuthn-guarded, redirecting to enrollment/login client-side — the SPA shell's trust model, one URL hop from a QR scan
    GET /rtttl the piezo tune composer — a standalone client-side page (no build step): paste or compose RTTTL, hear it through a Web Audio square-wave oscillator that mimics the buzzer (corpus-accurate defaults d=4/o=6/b=63, dotted notes in both positions, 10 ms inter-note gaps), see it on a piano-roll canvas, start from 12 corpus presets. "Send to device" is deliberately disabled — the firmware has no chime/play verb yet (Commands → not in the firmware), and the dashboard does not invent relay verbs the glass never agreed to speak. The page exists so melodies are composed and auditioned before the engine ships, the same probe-before-build order the lockout used
    GET /{path} the built PWA (SPA fallback)

    A vulnerability this table is honest about (found & fixed)

    The SPA catch-all (GET /{path}) decoded %2e%2e before routing — an encoded-traversal request on the local port could read files beside the app, including .sticky_auth.json (the JWT secret). Found by the supervisor's route sweep while shipping /api/frames, fixed by containment (resolved paths must stay under dist/), and the jwt_secret was rotated — every session invalidated, passkeys kept. It's recorded here rather than buried because this page documents trust boundaries: capability URLs are only as good as the file server refusing to walk ...

    Running it·

    cd docs/dashboard
pip install -r requirements.txt        # fastapi uvicorn pillow pyjwt webauthn cryptography requests
(cd frontend && npm install && npm run build)
STICKY_AUTH_BOOTSTRAP_TOKEN=$(openssl rand -hex 12) ./run.sh   # :8787
    • Public: Cloudflare Tunnel sticky (~/.cloudflared/sticky.yml) routes sticky.cagatay.my → localhost:8787; run cloudflared tunnel --config ~/.cloudflared/sticky.yml run sticky.
    • LAN without the tunnel: STICKY_TLS=true mints a self-signed cert (tls.py) because WebAuthn needs a secure context; http://localhost:8787 also qualifies for local dev.
    • Dev loop: cd frontend && npm run dev (Vite proxies /api + /auth to :8787).
