    Envelope command surface (what use_device reaches)·

    Envelopes are {type:'invoke', prompt}; prompt is parsed as <verb> [args], unknown text answers the help string (never silence). Replies ≤ 8000 B; images ride as hosted URLs. Shipped at 0.14.18-m12 — the per-verb reference with exact reply shapes lives in Commands:

    verb does
    render_ui <card-json> render card → reply rendered card_id=<committed id>
    say <text> text card on the panel + ack chime, no network wait
    screenshot framebuffer → hosted PNG URL (render ground truth)
    page home\|status\|sensors\|settings\|wifi\|back\|next\|prev relay twin of stickyOS nav (parity rule)
    status machine-readable JSON + human summary field
    sensors [card] live I²C JSON; card also paints the sensors page
    miccheck [s] record → RMS/peak verdict live/SILENT (no upload)
    ask <text> owner-scoped agent turn via /api/devices/ask → card
    voice [s] PDM record → /api/media → ask with audioUrl (= AI button)
    sleep [s] reply → goodbye card → deep sleep (EXT1/timer wake)
    ota [channel] stage + sha-verify → reply → reboot into rollback-armed trial

    Planned, not dispatched: image / stream (blit path exists in the renderer), wake (radio is off — button/timer only), reprovision (heartbeat-401 reopens the portal automatically).

    Card spec (render_ui) — as shipped·

    Types: text · list · kv · composite (≤4 parts) · qr (scannability-honest) · keyboard · menu · buttons (≤4, 56 px bottom bar) + title/footer/card_id on any card. Full spec with examples and the refresh policy: Cards.

    Button tap → routed to the shell if the page owns it, else ui_tap device note → owner's activity feed → the agent answers with the next card. The screen is a conversation.

    Refresh policy·

    • buttons/text/list/kv → monochrome full (~600 ms class)
    • status-bar clock, stream frames → partial
    • photo/image cards with gray4:true → 4-level full (slowest, prettiest)
    • rate-limit: min 1.5 s between refreshes, coalesce bursts (queue, render last)

    Voice-ask pipeline·

    hold AI btn ≥1s → chime + "listening" partial-refresh glyph
→ PDM 16kHz/16-bit → PSRAM ring (cap 15s) → release → WAV
→ POST /api/media (device token) → audioUrl
→ POST /api/devices/ask {deviceId, token, audioUrl}     ← NEW backend route
→ backend: transcribe → owner-scoped agent turn → {text, card?}
→ card rendered; text also POSTed to /api/devices/transcript (durable)
Fallback until /ask ships: transcript + event, agent replies via relay envelope.

    Audio out — honesty section·

    Hardware = magnetic buzzer on LEDC PWM. Tier 1 (ship): event chimes, melodies (RTTTL parser, ~1 KB). Tier 2 (experiment): 8-bit PCM via high-freq PWM duty modulation — known to produce barely intelligible speech on magnetic buzzers; we measure, we don't promise. Real TTS playback needs hardware we don't have; the honest framing is chimes + text-on-screen.

    Tasks / RTOS layout·

    task core prio job
    node 0 5 heartbeat/poll/dispatch (network-bound)
    render 1 6 canvas + refresh queue (SPI-bound, owns display)
    input 1 7 buttons ISR→queue, GT911 INT, touch regions
    audio 0 8 PDM capture bursts
    housekeeping 0 3 battery/RSSI sampling, status bar, sleep policy

    Single event queue (AppEvent superset of demo's) so the demo's page framework keeps working underneath during bring-up.

    Provisioning UX·

    First boot (or reprovision, or heartbeat-401): e-ink renders a setup card with QR (WIFI:S:tiny-XXXX;T:WPA;P:tinysetup;;) + SN + steps; softAP portal identical to Nicla's (/info advertises {kind:"reterminal-sticky", version, mac}). The tiny iOS app flow "add device → join AP → POST /setup {device_id, token, networks[]}" works with zero app changes — enrollment (POST /api/devices) already happens app-side.

    Security posture (inherited, non-negotiable)·

    • flash carries ONLY the device-scoped token (revocable; heartbeat-401 self-heals to portal)
    • OTA artifacts sha256-pinned, hosts pinned, staged to ota_1, trial-boot + self-test before commit; tiny_boot judges, tiny_ota only fetches
    • every socket has a timeout; no silent envelope execution (buzzer blip / LED)

    Build & release discipline (paid for on 2026-08-25, m12 night)·

    Three rules, each purchased with a real incident the same evening two agent lanes shared one checkout:

    1. Clean-worktree builds. An OTA image is only evidence if it reproduces from a committed sha: git worktree add /tmp/sticky-<label> <sha> and build there, never in the shared tree. Incident: an image built mid-edit shipped as 0.14.2-m12 — a label no commit carries — with page/tap answering but scroll unknown and a pre-M10 help string: three eras in one binary.
    2. Version labels are monotonic, even when the label was an accident. A published label is burned; the fix ships as a bump above it (0.14.3 above the phantom 0.14.2), never a re-use, so fw in a status reply names at most one image.
    3. Functional receipts over version fields. A deploy is verified by making the new surface answer (probe the verb, read the JSON, screenshot the glass), not by reading the version string — the version string is data inside the image and lies exactly when the build process does. Incident: deployed "0.14.2" failed its own superset claim (rotate yes, scroll no) under live probes. Structural fix (0.14.10): TINY_FW_COMMIT — a git sha injected at build time (not configure time; the stale-sha-on-incremental gap is the exact collision class being retired), with a --dirty suffix that is honest about uncommitted trees, surfaced as fw_commit in every status reply. Receipts still outrank strings — but the string can now prove ancestry instead of asserting it. (Fitting detail: version 0.14.10 itself exercises the numeric ver_cmp — lexicographic comparison would order 0.14.10 below 0.14.9.)

    A fifth rule was purchased across three incidents in one night, all the same class — a shared worktree between agent lanes eats hunks between the editor and git add (00356b2's status hook, f6a46fb's torn tail committed with BUILD_EXIT=1, 32d0e14's clobbered feed that rollup constant-folded to null and dead-code-eliminated an entire feature out of a green bundle — the build was honest, the source was incomplete). The rule: claim a feature only after string-verifying it in the built artifact, never from the memory of writing it. Casualty #7 sharpened it: a unit test passed while the route it guarded was already gone, because the test exercised the function directly and never the route — test the surface a consumer touches, not the code you remember wiring to it — and verify at the right depth: a later crash-loop shipped through an ast.parse gate because the file was syntactically perfect and ordered wrong (a regex insert landed before the definitions it used); the gate now imports the module, because parse checks grammar while import runs the code, and only one of those is what production does. The same night added the edit-side twin: a version bump applied with sed silently did nothing (sed exits 0 whether or not it matched) and the lane read its pre-edit grep as if it were the result — two firmware versions rode out under one string until a self-caught collision commit (0.14.18) fixed it. Read back the state after the edit, never the intent before it — the same lane had written that hazard up twice for others before tripping it, which is the strongest argument that these are structural rules, not personal failings — and once, the race ran the other way: a sibling's live-wire field-name correction landed inside this documentation's own commit window, making the docs more correct than their author.

    Rule six arrived the night fw_commit shipped, when the new field caught its first offender within hours: the glass was found running 9cdf43cf-dirty — the base commit a fine ancestor, but the -dirty delta is by definition unknown code, most plausibly a sibling lane's race hunk baked into the binary. The rule: never publish an image whose fw_commit is -dirty or unpushed — an artifact that cannot name its exact tree cannot be audited, rolled back to, or reproduced. A day later the field's one blind spot surfaced: the sha is read from git, but the source is read from the working tree — in a shared tree those are two different things. A "build green" receipt named a commit that cannot compile; it was green only because a sibling's repair sat uncommitted beside it. The fix is structural: publish builds happen in a clean detached worktree (git worktree add /tmp/wt <sha>), where describe --dirty must print a bare sha and no lane's half-finished hunks can ride along. And rule 6 gained its amendment: global --dirty trips on tracked logs and other lanes' docs edits that are not in the image — the precise gate is git status --porcelain -- firmware/ empty. Keep the rule, aim it at the right file set. 0.14.14 was the first publish built this way; 0.14.16 and 0.14.18 followed, each answering a bare clean fw_commit from the glass — a chain now, not a lucky first.

    The same night also produced the advertise-only-what-dispatches invariant in its sharpest form: the heartbeat capability list and the dispatcher's branch table must be generated from the same truth, because they drifted twice — first in git (caught by review), then on glass (caught by probes).

    And a fourth rule, from the night an OTA was deferred for a phantom finger: the glass is a shared, single-user surface — probe etiquette applies. An agent lane announces on-glass probe sequences before running them, restores the previous page after, and stands down entirely when the events feed shows a human actively using the device. With one correction paid for the same night: a tap in the feed is not proof of a finger. The relay tap verb produces events indistinguishable from touch — the builder once stood down for hours deferring to a "human" that was another lane's probe. Attribute activity before deferring to it. Read-only verbs (status, sensors, bare scroll) stay fair game — they answer without repainting anything.

    The fifth rule was minted by a near-miss, not an incident: an OTA must prove ancestry before it publishes. A version number ordering is not enough — a build named 0.14.5 was minutes from publishing after 0.14.6 was already on glass (the builder's tree predated the hotfix), which would have silently rolled back the label-sniff security fix while looking like a routine update. The check is mechanical: the commit currently deployed must be an ancestor of the tree being flashed (git merge-base --is-ancestor <on-glass> <build>), and "what is on glass" comes from a live status probe, never from memory. The supervisor's block landed with the build already staged. The audit that followed located the root cause in code: the device's own trigger is direction-blind (strcmp difference, not comparison), so the firmware would install a stale pointer as faithfully as a fresh one — integrity checked, direction unchecked. The fix shipped as 0.14.9: numeric ver_cmp (unparseable = incomparable = refuse, fail closed) with a loud force:"1" override — and the publisher-side ancestry check stays in force. Two guards, one on each side of the wire.
