    NETWORK + NODE + OTA Stack Audit — firmware/main·

    Auditor: tiny (sub-agent #1/2), 2026-08-25. Scope: tiny_node.cpp (363L), tiny_wifi.cpp (79L), tiny_ota.cpp (188L), tiny_upload.cpp (95L), tiny_config.cpp (193L), all headers in tiny/, plus tiny_main.cpp for the boot wiring. fw version at audit: 0.8.1-m8.

    P0 — ship blockers·

    P0-1 · 401 → forget_identity() + reboot with NO provisioning portal = permanent brick·

    • tiny_node.cpp:264-268 (relay poll) and tiny_node.cpp:308-312 (heartbeat): a single HTTP 401 wipes device_id/token from NVS and calls esp_restart().
    • tiny/tiny_provision.h declares tiny_provision_start() — there is no implementation anywhere in the tree (grep confirms zero references outside the header). After the wipe, the fresh boot lands in tiny_main.cpp:90-94 — "waiting for device_id+token (config incomplete)" — a state recoverable only over a serial cable ({"config":{...}} line console, tiny_main.cpp:96+).
    • Threat model: 401 does not only mean "owner revoked me". A backend auth deploy bug, token-store hiccup, or misrouted request that answers 401 once destroys a good identity irreversibly. The comment at tiny_node.cpp:3-4 even admits the portal is a future milestone ("-> portal once M3b lands") while the wipe is live today.
    • Compounding bug: tiny_config_forget_identity() → rewrite_without() (tiny_config.cpp:167-190) returns an error if tiny_config_load fails (e.g. corrupt blob), the caller ignores the return and reboots anyway → potential 401→reboot→401 hammer loop against the backend.
    • Fix (minimum shippable): require N (≥3) consecutive 401s across ≥60s before wiping; never wipe while tiny_provision_start is unimplemented — degrade to a "re-auth needed" card + slow retry instead; check forget_identity()'s return before restarting.

    P0-2 · Wi-Fi drop is unrecoverable at runtime; all-networks-fail at boot parks the device forever·

    • tiny_wifi.cpp:24-30: on WIFI_EVENT_STA_DISCONNECTED the handler retries esp_wifi_connect() exactly 2 times (s_retries < 2), then sets the FAILED bit and stops. After boot, nothing ever waits on that bit and nothing ever calls tiny_wifi_connect() again — s_up stays false forever.
    • tiny_node.cpp:304: the node task's only reaction to wifi-down is vTaskDelay(2000); continue; — an infinite polite wait for a flag no one will ever set. Router reboots → device is offline until battery death or a power cycle, silently, with a stale card on the e-ink.
    • Boot path: tiny_main.cpp:84; if every SSID fails, tiny_wifi_connect returns ESP_ERR_WIFI_NOT_CONNECT (tiny_wifi.cpp:75-76) and app_main just logs it — no retry loop, no backoff-and-rejoin, no portal (see P0-1). One bad radio moment at power-on = offline appliance.
    • Detail: s_retries is written from the wifi event task and reset from the caller task with no synchronization (tiny_wifi.cpp:19,66) — benign today, racy once reconnect logic lands.
    • Fix: a supervisor path — when !tiny_wifi_is_up() for >30s, re-run the roaming list with exponential backoff (30s→5min cap); at boot, retry the join loop instead of giving up once.

    P0-3 · Relay envelopes silently LOST when the poll response overflows 4 KB (matches the observed "no reply after 45s" bug)·

    • tiny_node.cpp:300: response buffer is static char resp[4096], while poll_relay asks for up to 5 messages (tiny_node.cpp:262, max:5). One render_ui envelope with a real card spec can approach the size alone.
    • http_evt (tiny_node.cpp:48-58) drops whole chunks once len + data_len >= cap → truncated JSON → cJSON_Parse returns NULL → poll_relay returns silently (tiny_node.cpp:270-271).
    • The backend hands envelopes out on the PUT — a dropped parse means those envelopes are consumed server-side and never dispatched, never replied to. The sender waits out its full 45s timeout. This is the exact symptom cagatay and the supervisor both hit today (411a887c…). It also violates the firmware's own stated rule (tiny_node.cpp:292: "never silence").
    • Fix: raise the buffer (PSRAM, 16–32 KB) and make truncation loud: track a truncated flag in sink_t; on truncation, retry with max:1, and reply "envelope too large" rather than dropping. Consider max:1 permanently — the loop runs every 5s anyway.

    P0-4 · Declared-but-never-defined inventory (headers with zero implementation)·

    Confirmed by grep across all .c/.cpp: the only mentions are in comments.

    Header Declared, never defined Product impact
    tiny/tiny_provision.h tiny_provision_start() No softAP portal. Device cannot be (re)provisioned without a serial cable — combined with P0-1 this is the not-shippable pair. iOS onboarding path does not exist.
    tiny/tiny_boot.h tiny_boot_early(), tiny_boot_wake_cause(), tiny_boot_is_trial(), tiny_boot_commit(), tiny_boot_deep_sleep() No deep sleep / power management at all. Latent mic-killer: tiny_audio.cpp:4 says the post-deep-sleep USB-JTAG pin-reclaim fix (GPIO19/20 release + mic-rail cycle, docs/RESEARCH.md §6) "is handled in tiny_boot_early()" — a function that does not exist. The day deep sleep lands, voice ask dies after every wake unless this is remembered. OTA judging meanwhile lives in tiny_node.cpp:317-325 (works, but contradicts the header's "ONLY tiny_boot judges" contract).
    tiny/tiny_stream.h tiny_stream_image(), tiny_stream_play(), tiny_stream_stop() No image/frame-stream rendering — the WiFi-native media plan (#778) has no device half.
    tiny/tiny_commands.h tiny_commands_dispatch() Command table split-brain: dispatch is hand-rolled inside tiny_node.cpp:193-257 with only render_ui/status/ask/voice/screenshot/ota. The header promises say, sensors, image, stream, sleep, wake, reprovision, help. The heartbeat advertises "say" as a capability (tiny_node.cpp:110) that the dispatcher cannot execute — an agent will call it and get "unknown command".

    P1 — fix before calling it stable·

    1. hb_fail is dead code. tiny_node.cpp:302,313 — counted, never read. No escalation exists for a failing backend: no backoff, no wifi re-join, no reboot-after-N-hours. Wire it to the P0-2 supervisor (e.g. `hb_fail

      = 10→ re-run wifi join;>= 40` → reboot).

    2. No retry/backoff on any HTTP call. Every call in tiny_node.cpp/tiny_upload.cpp/tiny_ota.cpp is single-shot. Timeouts ARE consistently set (15s default tiny_node.cpp:42, 30s upload/OTA tiny_upload.cpp:74/tiny_ota.cpp:127, 80s ask tiny_node.cpp:158) — good — but one lost packet fails a heartbeat/reply/event outright. Replies (tiny_node.cpp:130) deserve 1–2 retries: a lost reply = the sender's 45s timeout even though the work was done.
    3. OTA version check trusts a hand-maintained string. tiny_ota.cpp:111 does strcmp(ver, TINY_FW_VERSION) where TINY_FW_VERSION lives in tiny/tiny_version.h ("0.8.1-m8") and must be bumped by hand each build. Forgotten bump → device reports "already up to date" forever and the channel is wedged (ESP_ERR_INVALID_VERSION, tiny_node.cpp:245-246). Fix: compare the manifest sha256 against the running partition's image hash (esp_partition_get_sha256 / esp_app_desc), or generate the version from git at build time (git describe → configure_file). Version-string-in-git is the same trap the Nicla hit.
    4. Node loop is fully serialized — one slow call starves everything. dispatch() runs inline in node_task; an ask blocks up to 80s (tiny_node.cpp:158), during which heartbeat (due every 30s) and relay poll stop → platform may mark the device offline mid-question, and other queued envelopes wait. Event drain (tiny_node.cpp:331-337) POSTs inline too: 8 queued taps × 15s timeout against a sick backend = 2min stall. Consider a worker task for ask, or at least accept the tradeoff in docs.
    5. Event queue drops silently on overflow / wifi-down. tiny_node.cpp:39 EVENT_QUEUE_LEN 8; tiny_node.cpp:362 xQueueSend(..., 0) → overflow returns ESP_ERR_NO_MEM and the tap vanishes (tap #9 while offline is gone forever). Queue is only drained when wifi is up. Acceptable for ui_tap, but log a drop counter and surface it in status.

    P2 — hygiene / hardening·

    1. ask_resp[8192] truncation (tiny_node.cpp:156): a long answer + card overflows → parse fail → user sees "(no text)" though HTTP was 200. Same silent-truncation pattern as P0-3; same fix (flag + honest message).
    2. resp[0] guard: poll_relay checks !resp[0] (tiny_node.cpp:269) — fine, but a non-JSON 200 body is also silently ignored; log it.
    3. URL buffers char url[160] (tiny_node.cpp:63, tiny_upload.cpp:65, tiny_ota.cpp:60): fine for https://tiny.technology, but a long custom api value silently truncates the URL → requests to a half-path. Guard snprintf return.
    4. OTA has no resume — a failed 3MB download restarts from byte 0 (tiny_ota.cpp:152-159). Acceptable on wifi; note it.
    5. OTA read_pointer reads status after failed perform (tiny_ota.cpp:77-83) — harmless but returns err vs ESP_FAIL inconsistently with http_json_t (-1 convention).
    6. Rollback window: a trial image that runs but never heartbeats 200 stays PENDING_VERIFY indefinitely — rollback only happens at the next reset. Pair with a "no heartbeat 200 within 10min while trial → reboot" rule in the (unimplemented) tiny_boot judge.
    7. Wifi creds + device token in plaintext NVS (tiny_config.cpp), no NVS encryption mentioned in sdkconfig review scope. Physical-access threat only; note for later.
    8. esp_wifi_stop() between roaming attempts (tiny_wifi.cpp:64) while the event handler may still fire esp_wifi_connect() — benign race, tidy when P0-2 lands.

    What's GOOD (keep)·

    • Every HTTP call has an explicit timeout; none can hang forever (the Nicla's 4.5-min silent hang lesson is applied).
    • OTA: host allowlist (tiny_ota.cpp:28-31), streamed download with size check against the slot, sha256 verified before esp_ota_set_boot_partition, rollback armed, validity marked only on first heartbeat 200 (tiny_node.cpp:317-325) — a genuinely correct A/B design.
    • Reply-before-reboot on ota verb (tiny_node.cpp:242-244).
    • Event queue decouples touch ISR path from HTTP (producer never blocks).
    • Upload builds its body in PSRAM and never logs the token.
    • Unknown envelope commands answer help text instead of silence (tiny_node.cpp:252-256).
