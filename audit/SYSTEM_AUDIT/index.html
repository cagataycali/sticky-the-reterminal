    SYSTEM + BOOT + POWER + AUDIO Audit — firmware/main·

    Auditor: tiny (sub-agent #2), 2026-08-25. Scope: tiny_main.cpp board.cpp sticky_power.cpp sticky_battery.cpp sticky_buzzer.cpp tiny_audio.cpp tiny_button.cpp pin_config.h (+ tiny_node.cpp/tiny_wifi.cpp read where the power story required it).

    P0 — must fix·

    P0-1 · tiny_boot.cpp does not exist; the USB-JTAG GPIO19/20 mic-mux fix is NOWHERE in the tree·

    • tiny/tiny_boot.h:14 declares tiny_boot_early(void); tiny_audio.cpp:4 and tiny/tiny_audio.h:4 claim "the Voice Companion deep-sleep lesson … is handled in tiny_boot_early()". There is no tiny_boot.cpp — not in main/CMakeLists.txt SRCS, not anywhere. grep -rn usb_pad_enable|USB_SERIAL_JTAG|gpio_reset_pin matches only comments/headers.
    • The known hardware bug (community-verified on this exact board): after deep-sleep wake, the S3 pin mux reclaims GPIO19/20 for native USB-Serial-JTAG → PDM mic is deaf on every post-sleep voice attempt. Required fix at earliest boot: USB_SERIAL_JTAG.conf0.usb_pad_enable = 0 + gpio_reset_pin(GPIO19/20) (+ the GPIO38 rail clean-cycle, which tiny_audio_record_wav does do, tiny_audio.cpp:63).
    • Latent today only because deep sleep is also never entered (P0-2). The moment P0-2 lands, voice breaks after the first wake. Also: tiny_boot.h promises the OTA trial/commit judge (tiny_boot_is_trial/tiny_boot_commit) — that logic was instead inlined into tiny_node.cpp:317-325, so the header is a lie; either implement the module or fix the docs/headers.

    P0-2 · Deep sleep is unreachable — zero callers, no idle timeout, no power-off gesture·

    • sticky_power_enter_deep_sleep() (sticky_power.cpp:47) is well-written (holds latch, kills EPD/touch/mic/SD/buzzer rails, EXT1 ANY_LOW wake on GPIO4) but has no call site anywhere. tiny_boot_deep_sleep() (tiny_boot.h:24) is unimplemented.
    • No inactivity timer (stock fw sleeps at 2 min idle), no long-press power-off (tiny_button.cpp:50 sets long_press_time = 2000 but registers only BUTTON_SINGLE_CLICK, tiny_button.cpp:57), and the M2 demo card literally shows a "Sleep" button (tiny_main.cpp:50) with no handler behind it.
    • Consequence: Wi-Fi + CPU run 24/7 → the 750 mAh pack dies in roughly half a day (see battery section), then hard-cuts with no warning.

    P0-3 · No low-battery protection at all·

    • sticky_battery_read() is called in exactly one place: the status verb's string (tiny_node.cpp:203-204). Nothing polls SoC periodically; nothing triggers a "battery low" card, an event to the backend, or a protective sticky_power_enter_deep_sleep() at ~5 %.
    • With P0-2 (always-on Wi-Fi) this guarantees repeated deep discharge of the 750 mAh cell — a battery-longevity and data-loss (mid-OTA brownout) hazard.
    • Also unused: PIN_BAT_CHG_EN (39) and PIN_EXTERNAL_POWER (9) — the firmware can't even tell it's on USB power, which is exactly the signal that should gate "always-on relay mode" vs "sleepy battery mode".

    P1 — should fix soon·

    P1-1 · Data race on the ask path: two tasks share static buffers with no lock·

    • tiny_node_do_ask() uses static char audio_url[256] and static char ask_resp[8192] (tiny_node.cpp:140,157). It is called from both the node loop (relay ask/voice envelopes, dispatch at tiny_node.cpp:223) and voice_ask_task (AI button, tiny_button.cpp:29). A button press during a relay-driven ask (an 80 s window! timeout at tiny_node.cpp:158) corrupts both requests. Needs a mutex or single-owner queue (the depth-1 s_ask_q protects only button-vs-button).

    P1-2 · One blocking loop = heartbeat starvation·

    • node_task is a single sequential loop; a dispatch that runs an 80 s ask, a 15 s record, or an OTA download stalls heartbeats (30 s cadence, tiny_node.cpp:326) and relay polls → backend sees the device offline exactly while it's busiest. Heartbeat cadence is also wrong in practice: 6 × (5 s delay + HTTP time) ≈ 40-60 s, not 30 s.

    P1-3 · Every HTTP call is a fresh TLS handshake·

    • http_json_t does esp_http_client_init … cleanup per call (tiny_node.cpp:60-81): relay poll every 5 s = a full TLS handshake every 5 s. This is the single biggest battery line-item (see below) and adds 1-2 s latency to every envelope. Use one persistent client / keep-alive connection.

    P1-4 · AI button semantics diverge from spec, and 8 KB stack is thin for the TLS ask path·

    • Spec (official stock UX + roadmap): hold AI = voice input, single click = home/wake. Implemented: single click fires a 6 s voice ask immediately (tiny_button.cpp:36-40); no long-press callback at all; Up/Down only post device_note events. There is no local "cancel recording" either — once clicked, the mic records 6 s no matter what.
    • voice_ask_task gets 8192 B (tiny_button.cpp:66) and runs record → media upload (TLS) → 80 s ask (TLS) → tiny_display_render_card. mbedTLS + cJSON + renderer nested in one 8 KB task is close to the edge; measure uxTaskGetStackHighWaterMark and bump to 12 K, or route the button through the node task instead of a parallel TLS client (also fixes P1-1).

    P1-5 · Boot uses ESP_ERROR_CHECK on non-essential peripherals → panic-reboot loop·

    • tiny_main.cpp:57-59: a transient failure in tiny_display_init() or sticky_buzzer_init() aborts → reboot → re-latch power → abort … forever, with no way for the user to power off (the latch is held before the check). Display is arguably essential; the buzzer is not. Degrade gracefully: log + render an error state where possible, and only hard-fail on board_init().

    P2 — polish / correctness notes·

    • Task WDT: enabled, 5 s, idle-task watch only (sdkconfig:1186-1191) — fine. No task subscribes explicitly; node_task's longest in-iteration blocking call is bounded (HTTP timeout 15 s / 80 s) and it never starves idle thanks to vTaskDelays. No interrupt WDT concerns seen. OK, but consider esp_task_wdt_add for tiny_node with a generous timeout so a wedged TLS stack reboots instead of hanging forever.
    • Serial card console loop (tiny_main.cpp:100-135): correct VFS/driver hookup, overflow drops the line silently (pos = 0, tiny_main.cpp:133) — prints nothing; emit CARD_RESULT overflow so the bench harness isn't left guessing. Config path does naive strchr for the inner { — a "config" value containing { inside a string would misparse; acceptable for a bench tool.
    • board.cpp wake path (board.cpp:34-47): re-drives HOLD/LOCK before gpio_deep_sleep_hold_dis() — correct order, good. PIN_POWER_LOCK is held HIGH permanently; stock semantics pulse it — verify against Seeed demo before the first battery-only power cycle test.
    • SD: PIN_SD_EN driven 1 at boot (board.cpp:96) with the comment "powered off" — verify polarity of the load switch; if EN=1 means ON, the SD rail idles powered for nothing (a few mA). Same check for PIN_TOUCH_EN/PIN_EPD_EN polarities in the sleep path.
    • Buzzer (sticky_buzzer.cpp): 2.4 kHz, duty 256/1024 (25 %), 60 ms — audible but quiet; for a passive buzzer max loudness is 50 % duty. sticky_buzzer_beep blocks its caller 60 ms (called from touch/button paths — fine). Only ONE chime exists; tiny_audio_chime(name) ignores its argument (tiny_audio.cpp:109), so "ask"/"ack"/"error" are indistinguishable to the user — cheap win: 3 distinct pitch patterns.
    • PDM capture (tiny_audio.cpp): pins/clk/slot config correct per official docs (CLK 19, DATA 20, mono 16 k s16); rail clean-cycle (150 ms off) present per recording — good. WAV header correct. Buffer in PSRAM — good. Full channel create/delete per recording is wasteful but safe. goto fail before i2s_channel_enable succeeded calls i2s_channel_disable on a non-enabled channel — returns an error, harmless, but check err. No gain/AGC — PDM raw may be quiet; worth a 4-6 dB software gain pass before upload.
    • Battery driver: reads only SoC; BQ27220 also gives voltage/current/temp — add to status and heartbeat body for fleet telemetry. No design-capacity programming (BQ27220 defaults may misreport SoC until configured for 750 mAh).
    • hb_countdown decrements after poll_relay even when Wi-Fi bounce continues earlier — cadence drift only, harmless.

    Battery-life estimate (750 mAh, current firmware behavior)·

    Model: Wi-Fi STA always connected, IDF default WIFI_PS_MIN_MODEM (no explicit esp_wifi_set_ps call found — default modem-sleep applies), relay poll every 5 s with a fresh TLS handshake each time (P1-3), heartbeat ~every 40 s.

    State Current (typ, S3 + radio) Duty
    TLS handshake + HTTPS round-trip ~120-150 mA ~1.5-2.5 s per 5 s cycle (~35 %)
    Connected idle, modem-sleep (DTIM) ~15-25 mA ~65 %
    E-ink refresh ~25 mA for 1-2 s negligible amortized

    Average ≈ 0.35·135 + 0.65·20 ≈ ~60 mA → 750 mAh / 60 mA ≈ 12 h (call it 9-14 h depending on RSSI and backend latency). Matches the "dies overnight" failure mode.

    What each fix buys: 1. Keep-alive TLS connection (P1-3): poll shrinks to ~0.2-0.3 s of radio → avg ≈ 27 mA → ~27 h. Biggest single win, pure software. 2. Adaptive polling (5 s only for ~2 min after interaction/envelope, else 30-60 s) + keep-alive: avg ≈ 12-15 mA → ~2-2.5 days. 3. Light sleep between polls (esp_pm + auto light-sleep, Wi-Fi beacon-only): avg ≈ 5-8 mA → ~4-6 days. 4. Scheduled deep sleep (wake on GPIO4 or timer every N min for a mailbox check; e-ink retains the last card for free): idle floor ~0.1-0.3 mA (latch + gauge) → weeks, at the cost of relay latency. None of 2-4 exists today; esp_pm isn't configured and no esp_wifi_set_ps(WIFI_PS_MAX_MODEM) option is exposed. Recommend: USB-powered ⇒ current always-on behavior; battery ⇒ tier 2 minimum, tier 4 below 20 % SoC — gated on PIN_EXTERNAL_POWER (GPIO9), which is currently unread (P0-3).

    Boot-order review (for the record)·

    app_main (tiny_main.cpp:55-99): log wake cause → board_init (latch first — correct and documented as a contract) → display → buzzer → splash+beep → 8 s photo delay → demo card → touch → audio → battery → buttons → config→wifi→node → serial console loop. Order is sound; failure handling is the issue (P1-5), and tiny_boot_early() should be the true first line once it exists (P0-1) — the USB-JTAG demux must run before any I2S/mic init after a deep-sleep wake.
