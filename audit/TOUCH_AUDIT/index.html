    Touch + Input Layer Audit — 2026-08-25 (auditor 1, full read)·

    Long-form audit, 2026-08-25. The stale-region race it dissects was closed in 0.9.x by publishing regions atomically with the card commit — the finding is kept because the dissection is the lesson.

    P0 — must fix·

    P0-1: The stale-region bug — unsynchronized region publication + regions published at draw time, not display time, with three unserialized render callers·

    The race, exactly:

    1. s_regions/s_region_count are plain statics with zero synchronization (tiny_display.cpp:82-83). Writer: draw_buttons() (tiny_display.cpp:85-109) runs on whichever task called tiny_display_render_card. Reader: tiny_display_button_regions() (tiny_display.cpp:111-115) runs on tiny_touch task (prio 5, 30ms poll). There are three concurrent render callers: the tiny_node task (tiny_node.cpp:168,178,198), the voice_ask task (via tiny_node_do_ask, tiny_button.cpp:27), and the main task serial card console (tiny_main.cpp:125). None hold a lock; the shared Canvas isn't locked either. A tap landing while draw_buttons is mid-write reads a torn s_regions[i] — struct assigned with label={0} at tiny_display.cpp:104 before strlcpy fills it at :105. A zeroed label printed through printf("label=\"%s\"") is empty/garbage → the observed label=?.

    2. Regions are committed ~2 seconds before the panel shows the card. draw_buttons updates s_regions during canvas draw (tiny_display.cpp:198), but the user still sees the old card until sticky_display_refresh_monochrome() (tiny_display.cpp:217, full refresh, 1–2s) completes. Any tap in that window hit-tests the invisible new layout. Conversely, a finger already down on the old card resolves at lift (on_tap_up, tiny_touch.cpp:62) against whatever regions exist at lift time → the observed tap-resolved-against-the-previous-card. The tiny_touch.h:2 region struct even has a card_id field designed for this — and tiny_touch_set_regions is an empty stub (tiny_touch.cpp:149-152), so card identity is never checked.

    The atomic fix (three parts, all small):

    // tiny_display.cpp
static portMUX_TYPE s_region_mux = portMUX_INITIALIZER_UNLOCKED;
static uint32_t s_card_gen = 0;   // bumped once per COMMITTED card

// in render_card: build regions into a LOCAL array during draw_buttons;
// publish only AFTER refresh returns ESP_OK:
esp_err_t err = sticky_display_refresh_monochrome();
if (err == ESP_OK) {
    taskENTER_CRITICAL(&s_region_mux);
    memcpy(s_regions, local_regions, sizeof s_regions);
    s_region_count = local_count;
    ++s_card_gen;
    taskEXIT_CRITICAL(&s_region_mux);
}

// reader returns gen: int tiny_display_button_regions(out, max, uint32_t *gen)

    In tiny_touch.cpp: snapshot gen at finger-down (touch_task where s_touching flips true, :99), re-read at lift in on_tap_up; if gen changed mid-press, drop the tap (the ground moved under the finger — iOS does the same when a view disappears under a touch). Additionally serialize the three render callers with one SemaphoreHandle_t display mutex around the whole render_card body (canvas + panel are also unprotected — concurrent serial-console + relay renders currently corrupt the framebuffer, a second latent P0 hiding behind the same lock).

    P0-2: No tap feedback is wired — and the parts all exist·

    on_tap_up (tiny_touch.cpp:62-86) prints a serial line and queues a device_note — no buzzer, no visual ack. Yet: - sticky_buzzer_beep() exists and works (sticky_buzzer.cpp:51, used at boot tiny_main.cpp:61), - tiny_audio_chime() exists and is wired for the physical AI button path (tiny_node.cpp:143,146) — but not for screen taps, - sticky_display_refresh_partial() exists in the vendored HAL (sticky_display.h:23) and is used by nothing; tiny_display_blit_1bit explicitly discards its partial flag (tiny_display.cpp:242).

    This is precisely why the user reported "touch doesn't work" while 12/12 taps were actually delivered. Fix: in on_tap_up, on a button hit: (a) sticky_buzzer_beep() immediately (<1ms, works from any task); (b) invert the button rect on the canvas and push it via sticky_display_refresh_partial() (~300-500ms, region-sized). Perceived latency drops from "nothing happened" to ~instant audio + sub-second visual. This must run before the network device_note round-trip, never after. Do NOT run the partial refresh on the touch task itself (e-ink busy-wait up to 10s, sticky_display.cpp:123) — queue it to the render owner.

    P1 — correctness / feel·

    P1-1: Fast taps (<~60ms contact) are silently dropped·

    kDebouncePolls = 2 at 30ms poll (tiny_touch.cpp:26,38) means a contact must span ≥2 polls; a crisp tap can be 40–60ms. The ghost-touch defence throws away real input. Better discriminator: GT911 reports contact area — GTPoint.size (gt911.h:21) is already read and ignored by touch_task (tiny_touch.cpp:92). Phantom points characteristically report size == 0. Accept single-poll contacts with size > 0; keep the streak rule only for size-0 points. Also: the GT911 INT pin is wired (PIN_TOUCH_INT, tiny_touch.cpp:134) but the driver reset leaves it as OUTPUT (gt911.cpp:71); INT-driven wakeup = lower latency + zero idle I2C traffic.

    P1-2: Hit-test uses the lift-off point, not the touch-down point·

    on_tap_up tests s_last_x/s_last_y (tiny_touch.cpp:71-72). Fingers roll on lift; iOS hit-tests the touch-down location and only requires lift within slop. Fix: hit-test s_start_x/s_start_y; capture provisional coords on poll 1 (today s_start isn't captured until the debounce streak completes, tiny_touch.cpp:99).

    P1-3: 5-second boot grace swallows taps with no user signal·

    kBootGraceMs = 5000 (tiny_touch.cpp:39,93-96) hard-drops every touch after init while the panel shows tappable buttons. Shorten to the observed ghost window, or use the size>0 filter from P1-1 and delete the grace entirely.

    P1-4: tiny_display_button_regions return-value contract is a footgun·

    Fills min(count,max) entries but returns s_region_count unclamped (tiny_display.cpp:112-114). Any future caller iterating the return over a smaller buffer reads uninitialized stack.

    P2 — robustness / polish·

    • Multi-touch truncated, not modeled — read_points(&p, 1) (tiny_touch.cpp:92); future pinch/two-finger needs maxPoints=2+ + per-id tracking (driver already returns id).
    • GT911 large-area flag (0x40) ignored — palm rejection is free by checking it.
    • vTaskDelayUntil catch-up burst (tiny_touch.cpp:110) — reset next after long stalls.
    • Starvation: touch never blocks on network (tiny_node_post_event queue-send timeout 0, tiny_node.cpp:356-363 — correctly designed). Landmine: any direct refresh call on the touch task can stall it seconds. Bump touch to prio 6 (above node) and keep it I/O-free.
    • Physical buttons (tiny_button.cpp): solid structure; missing chime on UP/DOWN click; BUTTON_LONG_PRESS configured (2000ms, :50) but never registered — AI-button long-press is dead.
    • tiny_touch_set_regions stub (tiny_touch.cpp:149) is the right long-term home for the fix — cards carrying card_id + button ids mean taps report semantic ids, not indices.

    Gesture roadmap (e-ink-appropriate)·

    The state machine already computes everything needed: s_start_*, s_last_*, streak (≈duration); the slop check at tiny_touch.cpp:65 already detects swipes — it just discards them.

    Gesture Detection E-ink verb
    Tap today's path + P0/P1 fixes button activate
    Swipe L/R adx > 80 && adx > 2*ady at lift page/card history nav (stock UX parity; synonym of UP/DOWN keys)
    Swipe from left edge s_start_x < 30 + right swipe back/dismiss card
    Swipe up from bottom s_start_y > 450 + up home card
    Long-press streak ≥ ~25 polls (750ms), < slop movement — fire AT threshold with buzzer blip context menu (pin / screenshot / ask-about-this)
    Drag do NOT build — e-ink can't animate tracking —
    Double-tap do NOT build — panel can't ack fast enough to make the rhythm learnable —

    Ordering: P0-1 + P0-2 together (two halves of the live bug report), then P1-1/P1-2, then swipes (~20 lines once tap machine is trustworthy), long-press last.
