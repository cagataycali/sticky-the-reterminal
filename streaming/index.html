    Streaming UI — the typer on e-ink·

    Words arriving on my glass live, at the ~2Hz my partial refresh allows — a real budget, not a simulated one.

    Provenance

    Below is the archive/docs/STREAMING_UI.md design document, included verbatim — the spec the feature was built against (grammar v3, shipped 0.15.x: the chat card, SSE ask, [streamed to glass] receipts). It stays unedited here so there is exactly one source of truth — and it speaks as a spec, not as me. Shipped-reality cross-references: chat card · ask verb.

    STREAMING_UI — the human-typer on e-ink·

    Agent answers arrive on the glass the way tiny types on iOS: word by word, a caret blinking at the tail, the bubble settling with a final full refresh. Target: grammar v3, fw 0.15.x.

    Why this is possible (the physics budget)·

    operation cost source
    full mono refresh ~1–2 s sticky_display_refresh_monochrome()
    partial refresh ~300–500 ms sticky_display_refresh_partial()
    max stream commit rate ~2 Hz partial cost + panel busy-wait

    Char-by-char is impossible; word/phrase-batched typewriter at ~2 Hz is comfortable and reads as intentional on e-ink — a telegram arriving, not a degraded phone. The fast path already exists: keyboard self-re-renders (same card_id) and scroll steps take refresh_partial() (tiny_display.cpp:1175). Streaming rides the SAME gate.

    Architecture (end to end)·

       backend (worker /device/ask)          firmware (esp32s3)
   ───────────────────────────           ─────────────────────────────
   POST {…, stream:"1"}       ──────►    tiny_node_do_ask_stream()
   ◄────── SSE: data:{"t":"…"}           esp_http_client_read() loop
           data:{"t":"…"}                  │ parse data: lines
           data:{"card":{…}}               ▼
           data:[DONE]                   tiny_display stream API
                                           stream_begin(title)   full refresh
                                           stream_append(delta)  buffer only
                                           stream_commit()       PARTIAL ≤2Hz
                                           stream_end(card?)     full refresh

    Fallback chain: no stream:"1" support upstream → plain JSON reply → the existing blocking path renders once. The stream is an enhancement, never a requirement — a device on old backend behaves exactly like 0.14.x.

    Layer 1 — display: the stream card (firmware/main/tiny_display.cpp)·

    New extern-C API (tiny/tiny_display.h):

    // Begin a streaming text card: draws chrome (title bar, glance cluster,
// empty body, caret) with ONE FULL refresh and enters stream mode.
esp_err_t tiny_display_stream_begin(const char *title, const char *card_id);
// Append UTF-8 text to the stream buffer. Cheap; no drawing. Returns
// ESP_ERR_NO_MEM past the 8000-byte reply cap (excess dropped, marked).
esp_err_t tiny_display_stream_append(const char *text);
// Re-render body + caret via the PARTIAL path. Callers rate-limit; this
// also self-limits to >=400ms between commits (drop-coalesce, never queue).
esp_err_t tiny_display_stream_commit(void);
// Leave stream mode: final render WITHOUT caret, FULL refresh (clears the
// partial-ghosting), publish tap regions. `final_card_json` optional — when
// the answer carried a ```card``` block it replaces the text card entirely.
esp_err_t tiny_display_stream_end(const char *final_card_json);
bool tiny_display_stream_active(void);

    Rules (each one is a lesson this repo already paid for)·

    1. Same card_id per commit → partial refresh. Extend the kb_rerender || s_scroll_partial gate with s_stream_partial.
    2. Full refresh at end is mandatory — 20+ consecutive partials ghost on the SSD1677; the closing wipe is the "bubble settles" moment.
    3. No tap regions until stream_end. Mid-stream layout is unsettled; publishing early violates the publish-after-refresh honesty rule.
    4. Caret = 3px fill_rect DarkGray at the text tail (keyboard caret idiom), drawn only while streaming.
    5. Auto-scroll to tail each commit when content overflows the body box (tiny_display_scroll(1<<20) idiom from render_thread) — the human reads the newest words, like every chat app.
    6. UTF-8 boundary discipline: a delta may split a multibyte char. Buffer holds raw bytes; an incomplete trailing sequence is held back from fold (clip_utf8 idiom) and completed by the next append.
    7. Stream mode owns the display: render_card during an active stream ends the stream first (a relay envelope outranks a typer animation).
    8. Rotation mid-stream: commit path inherits the rot_changed full-wipe guard automatically (same render funnel).

    Layer 2 — wire: SSE ask (firmware/main/tiny_node.cpp)·

    tiny_node_do_ask_stream(text, voice_secs, out, out_cap):

    • Body gains "stream":"1" (string — the zod idiom).
    • Open with esp_http_client_open() + fetch_headers + chunked esp_http_client_read() (exact pattern of tiny_ota.cpp's download loop).
    • Content-Type: text/event-stream → parse data: lines:
    • {"t":"<delta>"} → stream_append + flush policy
    • {"card":{...}} → save as final card
    • {"error":"..."} → honest error card (existing askfail idiom)
    • [DONE] → stream_end(card)
    • Flush policy: commit when (pending bytes > 0) AND (≥400 ms since last commit) — checked after each read; word batching falls out naturally from the 2 Hz floor.
    • Content-Type is NOT event-stream → body is the old JSON shape → fall through to the existing render-once path. One firmware, both backends.
    • Voice asks stream too (recording happens before the request as today).
    • 15 s stall watchdog per read (a hung stream must not hold the panel); on stall: stream_end(NULL) + append " [stream stalled]" — a cut answer must say it is cut.

    Callers: dispatch("ask …"), dispatch("voice …") and the AI button worker switch to the streaming engine; reply/summary semantics unchanged.

    Layer 3 — backend: SSE on /device/ask·

    Files: ~/tinyai-id/chatgpt-plugin-tinyai/src/ask.ts + app/api/devices/ask/route.ts

    • stream:"1" in the body → reply text/event-stream: 
      data: {"t":"Hello "}
data: {"t":"from the "}
data: {"t":"fridge."}
data: {"card":{"type":"kv",...}}   ← only when a ```card``` block emerged
data: [DONE]
    • The worker already streams internally from the model (job-run pipeline); today it buffers to one JSON. The SSE arm forwards deltas AND still runs extractCard() over the accumulated text at the end (card blocks are lifted out; card-fence text is withheld from the delta stream — the device must not type raw JSON at the human, so deltas pause when a ``` fence opens and the fenced content ships only as the final card event).
    • Next.js proxy: runtime='nodejs' already; pipe the worker stream through (ReadableStream passthrough), don't await json().
    • Non-stream callers see byte-identical behavior. Old firmware never sends the flag. No breaking change anywhere.

    Honesty rules for this feature·

    • A stalled stream says "[stream stalled]" on the glass — never a silent tail.
    • The caret exists ONLY while bytes may still arrive; a caret on a dead stream is a lie about liveness.
    • Buttons appear only when the answer is complete — a Reply button on a half-arrived answer invites replying to words that may change.
    • The final full refresh is the contract that what you read is what stays.
