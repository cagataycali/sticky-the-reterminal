    RESEARCH — everything we verified before writing a line of firmware·

    Long-form. The pre-firmware research ledger, dated 2026-08-25 and left as written: what was checked, against what source, and what turned out wrong later is marked where it happened.

    2026-08-25, tiny. Sources: live device on this desk, official docs (seeedstudio.com/sticky/docs), Seeed demo sources (vendor/), the playground registry, ~/strands-nicla firmware, ~/tinyai-id backend source.

    1. The device on the desk·

    Verified with esptool against the real unit (arrived 2026-08-25, a day early):

    • ESP32-S3 QFN56 rev v0.2, dual core 240MHz + LP core, WiFi + BT5 LE
    • 8MB embedded PSRAM (AP_3v3), 32MB quad flash (Winbond, ef/4019)
    • MAC b8:1f:3f:d7:23:60, crystal 40MHz
    • USB bridge: WCH CH343 → /dev/cu.usbmodem5C843358881
    • 921600 read-flash failed twice through the hub chain ("serial noise or corruption"); 115200 is reliable. Expect ~45 min for a full 32MB dump; use 460800 for app-size writes and fall back on error.
    • Stock firmware serial console at 115200 printed garbage — stock log baud unknown, irrelevant once we own the firmware.

    2. Official pin map (hardware-overview, cross-checked w/ community + demo pin_config.h)·

    Subsystem Pins Notes
    e-paper SPI2 SCK13 MOSI/SDI14 CS15 DC16 RST17 BUSY18 EN47 SSD1677-class, 800×480, 1-bit + 4-gray modes
    microSD shares SPI2, CS8 never drive concurrently with display transfer
    Touch GT911 I²C0: SCL2 SDA3 INT21 RST41 EN42 y-axis mirrored in community firmware (800-y) — verify on ours
    Sensor bus I²C1: SCL0 SDA1 SHT40 + LSM6DS3TR-C (INT=GPIO7, now official) + PCF8563 + BQ27220@0x55
    PDM mic CLK19 DATA20 ⚠ deep-sleep wake pin-mux bug, §6
    Mic power GPIO38 (TPS22916 load switch) community-sourced; demo's sticky_microphone is ground truth
    Buttons AI/PWR=4 (EXT1 wake), UP=5, DOWN=6
    Buzzer PWM GPIO48 official
    USB serial TX43 RX44
    Power latch HOLD=45 (keep HIGH), LOCK=46 community source only — official page omits it; demo's sticky_power.cpp is ground truth. Get this wrong → device powers off at boot.

    3. Seeed's ESP-IDF demos are a complete HAL (vendor/)·

    Sticky_dashboard_demo (ESP-IDF v5.4) contains everything hardware-touching we would otherwise write blind:

    • components/: seeed_epaper (the display driver!), gt911, bq27220, button (espressif iot_button), debug_logging
    • main/devices/: sticky_display|touch|microphone|buzzer|power|imu|sht40|rtc|sdcard|battery|charger|buttons — clean C++ modules over the components
    • main/board/: board_init() = power latch + shared I²C1 bus + SD defaults; modules reuse board_sensor_i2c_bus()
    • main/app|pages|ui/: AppState/AppEvent page framework + Canvas
    • Display API — three refresh modes, exactly the primitives render_ui needs:
    • sticky_display_refresh() — 4-gray full (~slowest, prettiest)
    • sticky_display_refresh_monochrome() — 1-bit full
    • sticky_display_refresh_partial() — 1-bit partial (status-bar clock pattern)
    • the driver applies a 180° rotation on refresh — framebuffer orientation matters for the screenshot tool
    • Integration patterns (esp-pages doc): read-on-page-entry (SHT40/battery), background monitor (IMU), capture-on-request (mic), input events (button/touch → AppEvent)
    • Deep sleep: AI button long-press → render sleep page → monochrome refresh → deep sleep; EXT1 wake on GPIO4

    Decision: we do NOT rewrite the HAL. firmware/ reuses vendor/Sticky_dashboard_demo/components via EXTRA_COMPONENT_DIRS and adapts the main/devices layer; our work is the tiny/* layer above it.

    4. tiny.technology device contract (read from ~/tinyai-id source — exact, not guessed)·

    Ported 1:1 from the Nicla (~/strands-nicla/firmware/tiny_node.py mirrors tiny-tech/src/mesh/relay-poller.ts):

    Verb Route Auth Shape
    enroll POST /api/devices session (app/CLI does it) {name, platform?, kind?, capabilities?} → {device_id, device_token} token returned once
    adopt POST /api/devices/adopt session {deviceId} → rotated token (old token dies instantly)
    heartbeat POST /api/devices/heartbeat device token in body {deviceId, token, capabilities} every 30 s; 401 = revoked → reopen provisioning portal
    poll PUT /api/devices/relay device token in body {deviceId, token, max:5} every 5 s → {messages:[{id, payload}]}, envelopes {type:'invoke', prompt}
    reply PATCH /api/devices/relay device token in body {deviceId, token, inReplyTo, payload} — payload = serialized JSON string {result[, images:[{url,format}]]} ≤ 8000 bytes
    media POST /api/media device token in body {deviceId, token, data:<b64>, contentType} → hosted URL. Nicla streams this raw-socket to avoid buffering; on ESP32-S3 with 8MB PSRAM we can buffer + esp_http_client
    transcript POST /api/devices/transcript device token in body {deviceId, token, text, label?, audioUrl?, durationS?} — outlives the 1 h relay sweep
    OTA pointer PUT /api/firmware/manifest device token in body {deviceId, token, channel} → {bundle:{url, sha256}} — pollable channel → manifest → artifacts

    Principles inherited from the Nicla (they're in the source comments for good reasons): - the device token is the only credential in flash — scoped, revocable; never the account bearer - every HTTP call gets a hard timeout (Nicla went silent 4.5 min on one hung socket) - no agent runs on-board — a command table maps envelope prompts to hardware actions; flash an LED/buzzer blip per executed envelope (nothing runs silently) - OTA: manifest pinned by sha256, artifact hosts pinned, downloader may never approve its own download (boot/trial/commit logic stays out of the OTA path)

    5. The one backend gap: "ask tiny" for a phoneless device·

    Nicla voice flow leans on the paired iPhone to record + transcribe on-device, then POST /transcript. The Sticky has no phone. Needed in ~/tinyai-id (we own it):

    POST /api/devices/ask {deviceId, token, audioUrl | text} → worker: transcribe (audio case) → run owner-scoped agent turn → reply {text, card?} (card = render_ui spec). Falls out of existing pieces: media upload already device-authed, transcript route shows the auth pattern, agent turns exist for every other surface. Until it lands, the fallback is: device uploads WAV + posts transcript-request event; a scheduled agent answers via relay envelope (slower, works today).

    6. Known hardware traps (from community voice-companion firmware — same physical device)·

    1. Deep-sleep wake kills the PDM mic: ESP32-S3 pin mux reclaims GPIO19/20 for USB-Serial-JTAG on wake. Fix at boot, before I²S init: USB_SERIAL_JTAG.conf0.usb_pad_enable=0; gpio_reset_pin(19/20); cycle mic rail (GPIO38 LOW 150 ms).
    2. Power latch: GPIO45 must go HIGH early in boot or the device just turns off.
    3. GT911 y-mirror: touch y arrives flipped (800 - y) in the community build — calibrate against our own driver during M2.
    4. Shared SPI2: SD and e-paper transfers must be serialized.

    7. Recovery research (the "how do we un-brick" answer)·

    • ROM download mode is unkillable: hold BOOT-equivalent (the reset hole / strapping pin) → USB bootloader, esptool always works. A bad app cannot brick the S3.
    • Official factory image: playground registry sticky-factory, mode flash, v1.1.0 = one 33,292,288-byte image at offset 0 (sha256 8b149c…17e4), browser-flashable (Chrome/Edge WebSerial) with an erase option, or by hand with esptool. Older versions 0.2.1–1.0.1 as GitHub releases with per-manifest sha256.
    • Our dump: full 32MB read-flash of the exact as-shipped unit (includes its NVS: factory calibration, SN, any per-device binding) — recovery/stock-firmware-32MB.bin. The official image restores firmware; our dump restores this unit byte-for-byte.
    • Re-pairing after restore: stock firmware re-enters Seeedash pairing; the SN survives in its own partition (part of why we dump all 32MB, not just the app).

    8. Stock firmware UX (what we replace, and the bar to clear)·

    Seeedash app: BLE pairing (SN shown on screen) → 2.4GHz Wi-Fi → device runs phone-free; OTA via app. Buttons: AI 3 s = on, both page 1 s = off, AI 1 s = voice note, any = wake; 2 min idle → sleep. Apps: Notes/Weather/Clock/Photos/Designs/AI-usage. Fonts via microSD fonts/*.fpack.

    Our provisioning replaces BLE-pairing with the Nicla AP portal (tiny-XXXX / tinysetup / 192.168.4.1, GET /info, POST /setup) so the existing tiny iOS onboarding works unchanged. BLE provisioning can come later as a nicety (NimBLE NUS), not a dependency.

    9. Sizing sanity·

    • Framebuffer 800×480: 1-bit = 48 KB, 2-bit (4-gray) = 96 KB — trivial in 8MB PSRAM; keep both a work canvas and a shadow copy for partial-refresh diffs and screenshots.
    • Screenshot as 8-bit grayscale BMP = 384 KB → b64 ≈ 512 KB upload, fine over Wi-Fi; 1-bit BMP = 48 KB. Start with 8-bit BMP (zero-dependency encoder), consider PNG (miniz) later.
    • Mic: 16 kHz/16-bit mono WAV, 10 s = 320 KB — buffers in PSRAM, uploads in seconds.
    • Partition plan for 32MB: nvs(24K) otadata(8K) phy(4K) factory(4M) ota_0(4M) ota_1(4M) assets-spiffs(rest ~19M) — factory slot holds our recovery-capable base build; OTA A/B for tiny_ota.

    10. Open questions for bring-up (M0/M1 will answer)·

    1. Does the demo build unmodified on IDF v5.4 + our unit? (M0 gate)
    2. Real partial-refresh latency + ghosting budget → render_ui refresh policy
    3. GT911 orientation on our unit
    4. Buzzer PCM experiment: LEDC @ ~40 kHz carrier, 8-bit duty modulation — audible speech or noise? (fun, non-blocking)
    5. Wi-Fi power draw vs 750 mAh: relay poll every 5 s will not survive days on battery → light-sleep between polls, or lengthen poll interval when on battery (heartbeat carries battery %, backend can adapt)
