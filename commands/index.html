    Commands — the envelope verb reference·

    Everything the Sticky answers to, exactly as tiny_node.cpp dispatches it — last audited against the tree at 0.18.0-m14, grammar v6 (the homepage pins what's verified on the glass, which may trail the tree by a version). Nineteen verbs, nineteen advertised: since 0.17.0 the heartbeat caps array and the dispatch table are in full parity (lock/unlock joined both at once, swipe — the old known gap — was fixed in the same commit, and glance entered both surfaces together in 0.18.0), so the dashboard's buttons light from a complete, truthful list. Envelopes arrive as {type:"invoke", prompt:"<verb> [args]"} over the relay; every verb replies (unknown input answers the help string — never silence). These are also the capabilities the heartbeat advertises, and the rule is: advertise only what dispatch actually implements.

    Send from any tiny surface:

    use_device invoke → prompt: "status"

    Display·

    render_ui <card-json>·

    Renders a card spec on the e-ink. Replies rendered card_id=<id> — the id the panel actually committed, so a mirror can claim "this IS what is on the glass" rather than "the last card I sent".

    render_ui {"type":"text","title":"Dinner","body":"Back at 19:30 — pizza in fridge"}

    say <text>·

    Put words on the fridge — no agent turn, no network wait. Renders a text card titled tiny (card_id=say) and plays the ack chime. Replies said (card on the panel).

    screenshot·

    Framebuffer → hosted PNG → replies screenshot: https://plugin.tiny.technology/media/…. This is render ground truth — the agent (and the dashboard mirror) see the actual panel, not a belief about it.

    page home|status|sensors|settings|wifi|ble|back|next|prev·

    The relay twin of every tappable navigation path in stickyOS (the M10 parity rule: anything a finger can do, an envelope can do). Replies page <arg> -> ESP_OK (card_id=…).

    rotate [0|90|180|270|auto]·

    The UI follows the body. Bare rotate reports; a degree value sets the layout rotation and holds it (manual mode — a human's choice outranks gravity); rotate auto hands the decision back to the accelerometer.

    {"rotation":90, "mode":"manual", "imu_last":"portrait-right", "imu_last_deg":90,
 "result":"ESP_OK", "summary":"rotation 90 deg (manual), imu says portrait-right"}

    Auto-rotate policy (deliberately small): commit only after several consecutive identical IMU readings — a ~600 ms visible e-ink refresh must never chase a wobble; flat on a table (flat) says nothing about which edge is up, so the last standing orientation wins. Coordinate invariant: the layout turns; the framebuffer, screenshot and touch coordinates stay in panel space — a tap aimed at a screenshot pixel still lands.

    tap <x> <y>·

    A synthetic tap in panel coordinates — the screenshot's own coordinate system — through the same resolver a finger uses. This is how a rotation gets proven without a human hand: tap where the screenshot shows the button, and see which button answers.

    {"tap":[400,440], "rotation":90, "result":"ESP_OK", "card_id":"home",
 "summary":"tapped 400,440 at 90 deg -> ESP_OK"}

    Together, screenshot → tap → screenshot closes the loop the agent needs to test the UI end-to-end with no one in the room.

    swipe <x0> <y0> <x1> <y1> (since 0.16.2, grammar v4)·

    A synthetic swipe in panel coordinates, driven through the same release classifier a finger uses — so what it proves is the real gesture grammar, not a parallel code path. This is how UX_SPEC §2 rules get verified over the relay: inject the vector, read the receipt, screenshot the consequence.

    // receipt shape since 0.16.6 (route-time, two stages named);
// "route" added in 0.16.7 (R-6b, tap and swipe both):
{"swipe":[400,60,400,300], "rotation":90,
 "accepted":"ESP_OK",          // classifier verdict at inject
 "routed":true,                // the route actually FINISHED before this reply
 "route":"ESP_OK",             // the route's OWN verdict (0.16.7, verified on
                               // glass): any esp_err name — ESP_OK = nav
                               // happened, ESP_ERR_NOT_ALLOWED = announced
                               // dead-end, ESP_ERR_INVALID_STATE = scroll with
                               // nothing to scroll (content fits), "none" = no
                               // route ran — before this field a dead-end and
                               // a nav returned identical receipts
 "card_id":"home",             // display-time, no longer inject-time
 "summary":"... -> ESP_OK, route completed; card_id is display-time"}

    The summary's third clause is one of: refused at classifier · route completed · route still running at reply time (slow render — probe again, not lost) · no route dispatched (accepted but a dead-end gesture).

    INVALID_SIZE means the travel stayed within the 24 px tap slop — refused rather than silently downgraded to a tap, because a probe that quietly becomes a different gesture proves nothing. Buttons and long-press still have no synthetic twin (press is not a verb yet), so those stay hand-verified.

    Probe under rotation: coordinates are panel space but the gesture is classified in logical space — under rotation:90 a panel-horizontal swipe is logically vertical and routes to scroll, not page-turn (live probe on 0.16.7: the same 200,240 → 500,240 vector answered route:ESP_ERR_INVALID_STATE — scroll with nothing to scroll — at 90°, and popped a pushed card at 0°). Read the receipt's rotation field before interpreting route, or pin the frame with rotate 0 first.

    History worth keeping: verdict batch #5 convicted the first receipt design using this verb — R-5 (a 40 px sub-slop swipe answered ESP_OK) and R-6 (card_id written at inject time raced the async route, same torn-read family as the M9 draw-time-regions lesson). Both fixed and VERIFIED ON GLASS at 0.16.6-m14 (6af1449, fw_commit 47821b73): the receipt waits for the route to finish and reports display-time state, with the accepted/routed stages separated so an accepted-but-dead-end gesture can no longer masquerade as success. Live probes against the panel: a bottom-band swipe answered "accepted":"ESP_OK","routed":true,"card_id":"home" with the card provably home, and a 20 px probe was ESP_ERR_INVALID_SIZE, refused at classifier. One correction to the record: R-5's original probe used 40 px of travel and called it "sub-slop" — but kTapSlop is 24 px (tiny_touch.cpp), so 40 px was always a legitimate swipe and its ESP_OK was correct; the receipt design (inject-time, R-6) was the real defect, and it is gone. On a device still running ≤0.16.5, let a follow-up status/screenshot — not the swipe reply — prove the consequence. tap got the same route-time contract (12 s wait, because a tap can trigger a blocking route like the ~8 s BLE scan; "routed":false means still running, not lost).

    Advertising gap — CLOSED in 0.16.8. From 0.16.4 to 0.16.7, swipe was dispatched but missing from the heartbeat's capabilities array, so the fleet's device list under-reported the surface. Fixed in 4dd7fcf and verified end-to-end on 0.16.8: use_device list now shows all 16 verbs, swipe included. The rule stands — advertise exactly what dispatch implements — and this section keeps the incident because under-advertising is the quiet failure mode of that rule.

    scroll [up|down|top|<±px>]·

    Moves an overflowing card body (text/list/kv/menu taller than the body box). Bare scroll just reports — the probe form; up/down step ⅔ of a view (the buttons' relay twin), top rewinds, a signed pixel count is probe-precise. Always clamped at the edges; on a card that fits, scrollable comes back false and nothing moves. A right-edge track+thumb scrollbar shows position on the glass; steps draw with partial refresh.

    {"offset":474, "content_h":1012, "view_h":356, "scrollable":true,
 "card_id":"scrolltest", "result":"ESP_OK",
 "summary":"scroll 474/656 px of 1012 content (ESP_OK)"}

    The reply carries the whole scroll model (offset / content_h / view_h), so scrolling is provable without a finger — the same probe-readable discipline as rotate and tap. Quirk (0.14.4): scroll 0 is indistinguishable from the bare report form (atoi returns 0 for both) — to go to the top, say scroll top, never scroll 0; the dashboard works around this the same way. (This verb also has a war story: its first landing was eaten by a shared-tree race and shipped as an advertised-but-unknown command — the incident behind the build-discipline rules.)

    Telemetry·

    status·

    Since 0.14.10 the reply carries fw_commit: a build-time-injected git sha with a --dirty suffix for uncommitted trees, so the version string can prove ancestry instead of asserting it (generated at build time, not configure time — stale-sha-on-incremental is the exact collision class retired). One caveat, stated when it shipped: on a shared worktree -dirty names the checkout's state, not necessarily the firmware's. Machine-readable JSON — the dashboard parses fields directly; a summary field inside carries the human sentence, so one verb serves both readers instead of two that can disagree.

    Fields: fw, grammar_version, poll_cadence, device_id, battery_pct, charging, wifi, ssid, rssi_dbm, heap_free, psram_free, uptime, card_id (what's on the glass right now), locked, auth_halted, summary. Provenance honesty: a gauge that didn't answer yields null, never false — "not charging" is a claim.

    Since 0.18.1 the reply also carries the §12 boot receipt when the boot measured itself: first_paint_ms + boot_path ("glance-wake" — a deep-sleep wake that skipped the splash and painted the glance-bearing home card before any network — or "cold-splash"). The acceptance (<2 s from wake to readable glass) travels in the field, same pattern as glance's refresh:"partial": the receipt is the reply, not a claim in the release notes. Omitted entirely when unmeasured — absent, not zero.

    The field's first days, kept as the case study they are. The first live receipt (0.18.1) read first_paint_ms: 3095, boot_path: "glance-wake" — a miss against the <2 s budget, quoted here as one. This lane also suspected the classifier (a post-OTA reboot claiming glance-wake); the builder's measurements vindicated it — OTA reboots read cold-splash (8158 ms measured, 8163 ms re-confirmed by this lane on 0.18.2), and the suspect 3095 was a genuine timer wake from a sleep 15 test. Retracted accordingly: the suspicion was filed, tested, and lost — which is how filings should die. 0.18.2 then shipped the paint-first wake (touch/audio/sensors/buttons/lock init deferred until after the home paint, whose only data dependencies are two millisecond I²C reads — battery and RTC; the lock chord arms a few hundred ms later on a path where the device is in the owner's hand by definition), and this lane measured the shaved path same-actor, fresh replies: sleep 15 → timer wake → first_paint_ms: 2496, boot_path: "glance-wake". Arc so far: 3095 → 2496 against 2000. 0.18.3 then added paint_breakdown {board_ms, display_init_ms} to the reply — instrumentation shipped specifically to arbitrate a two-lane disagreement (floor-honest ≤2600 vs. keep-2000-fix-the-refresh) under the project's rule that numbers outrank seniority. This lane's same-actor wake measurement on 0.18.3 delivered the verdict: first_paint_ms: 2496, breakdown 279 + 120 = 399 ms — init is a rounding error; the ~2.1 s remainder is shell render + the e-ink full flash. That verdict then lasted exactly one ruling — and the correction is the better lesson. Partial-first assumed the sleep-persisted card is a valid partial baseline; the SSD1677's refresh baseline does not survive power-down, so a partial against it is the §0 collage class, and doing it safely is a real baseline-persistence package with its own failure mode (battery dies mid-sleep, persisted frame drifts from glass). Batch #18 reversed with the physics: acceptance ratified at ≤2600 ms by receipt, ~3 s human-perceived (cold-battery headroom), and the hybrid paint stays on the books as the law's named successor — <1500 ms when it ships, "so nobody re-litigates". The arc in full: 8158 → 3095 → 2496 measured, a two-lane disagreement arbitrated by instrumentation, a designer ruling reversed by deeper physics, and a law that ends by naming what replaces it. Then the epilogue nobody scheduled: 0.18.4 (in tree, staged) ships the successor by dissolving the physics objection instead of overruling it — the baseline that "does not survive power-down" is not trusted but reconstructed (goodbye card body+rotation noted in RTC RAM at sleep, redrawn on wake as the explicit previous plane, then write_bitmap_diff partial ~300–500 ms claimed; no note → honest full flash; a lazy gray-clean 6 s later self-heals waveform residue). Both rulings were right in what they defended — #16's "wrong refresh mode" and #18's "stale baseline is the collage class" — and the implementation satisfies both. Numbers pending: the ~300–500 ms is the tree's claim; the <1500 ms law tightens when first_paint_ms says so from the glass. Cold boots for scale: 8158/8163/8164 across three consecutive OTA reboots, all correctly cold-splash — three same-actor receipts, one from each measuring lane.

    grammar_version (0.14.4) is the field consumers should gate on: the verb grammar is a 3-consumer contract (dashboard, iOS StickyPanel, relay agents) and this integer bumps on any change to a verb, its arguments, or a reply shape. It exists because a version string is data inside the image and can lie about content — proven the night an uncommitted build shipped as "0.14.2" advertising a verb it didn't dispatch. v1 = the 14-verb grammar of 0.14.3; v2 (0.14.11) = the messages dialect — the messages verb family plus the m: button-id namespace (inbox / thread / compose).

    sensors [card]·

    Every onboard sensor, read live over I²C1 — no network either way. Bare verb replies JSON; sensors card also paints the sensors page on the glass. Since 0.14.11 the BQ27220's mAh fields carry their own provenance: the gauge had reported full_charge_mah: 7500 on a 750 mAh pack since first read — off by exactly 10× — and the brief carried it as a known-lying field for two days. The fix reads DesignCapacity (standard command 0x3C) and adds design_mah + pack_mah + mah_trusted (field names measured off the live wire, not predicted — an earlier draft of this line said design_capacity_mah, which the firmware never emitted), so the absolute-mAh fields now say whether to believe them instead of asking the reader to know the datasheet.

    🩹 A bug that lived on the wire for three builds (fixed + wire-verified on 0.14.14): the provenance fields pushed the reply past its buffer and a strlcpy whose return value was discarded truncated it silently — sensors shipped JSON cut mid-token at byte 767 while claiming ESP_OK, measured twice byte-identical. Two lessons survived the fix. The builder's own probe showed the cut and it was misread as sed clipping the line — a truncated receipt is itself evidence, not noise in the pipeline that carried it. And the dashboard's answer was defense-in-depth: a salvage parser (bracket/string-state scan, unit-tested against the actual truncated wire capture) plus a truncation banner — recover what's intact, confess what isn't. This loop re-measured on 0.14.14: complete reply, parses clean, errors[] and all — the published receipt agrees (767 B invalid → 840 B valid). And the defect was then treated as a class, not an instance: 0.14.16 (verified on glass — this loop's probe and an independent check both parsed clean) kills the same silent truncation on status and messages unread before it fires, and a follow-up audit swept every remaining fixed buffer on the reply paths. DesignCapacity measured at 7500 on the 750 mAh pack — and the fix was deliberately not a blind ÷10: if the gauge's CC-Gain is also off by 10× the errors cancel and today's working percentage would break, so mah_trusted:false stands (with an errors[] confession in the JSON) until a 30-second unplug test — owner's hands required — decides which of two opposite fixes applies.

    {
  "temperature_c": 24.1, "humidity_pct": 41.2,          // SHT40
  "orientation": "flat", "accel": {"x":…}, "gyro": {…}, // LSM6DS3TR-C (gyro power-cycled per read, ~110 ms)
  "rtc": "2026-08-25T21:04:11Z", "rtc_zone": "UTC",
  "clock_source": "sntp",                                // sntp | rtc | none — the field is honest about provenance
  "battery": { "percent":…, "voltage_mv":…, "current_ma":…, "remaining_mah":…,
               "full_charge_mah":…, "health_pct":…, "cycle_count":…,
               "temperature_c":…, "charging":…, "full":…, "present":…,
               "design_mah":…, "pack_mah":…, "mah_trusted":… }  // BQ27220
}

    Read mah_trusted before you believe any mAh field (0.14.18-m12). design_mah is what the gauge says the pack is (DesignCapacity 0x3C, measured on this device: 7500); pack_mah is the nameplate (750, docs/hardware.md). They disagree by 10x, so mah_trusted is false and errors[] carries bq27220: design 7500 mAh vs 750 mAh pack - mAh untrusted. design_mah:0 means the read failed. percent comes straight from the gauge register StateOfCharge (0x2C) and is NOT computed from these fields — but see the JOURNAL entry for why a 10x design capacity can still bend the percentage in the middle of a discharge even while it is right at both ends. The three keys are additive; nothing in the dashboard consumed the mAh fields.

    miccheck [seconds] (1–10 s, default 2)·

    Records PDM audio and replies RMS/peak instead of uploading: {"verdict":"live|SILENT","rms":…,"peak":…,"nonzero_pct":…,"samples":…,"secs":…}. A dead post-wake mic mux reads flat zeros; a live mic reads the room's noise floor — this is how sleep → wake → mic gets proven with nobody home to speak.

    The device has exactly three microphone paths

    voice, ask-via-AI-button, and miccheck — and a pocket device must be able to gate all three at once. Since 0.17.1 it does — at a single point: the D-UX5 ruling ("guard the audio entry point, not a list of verb names") proved out the hard way when the docs lane's on-glass probe caught 0.17.0's verb-name gate leaving miccheck live on a locked device. The gate now lives in tiny_audio_record_wav, the funnel every capture path shares — verified by A/B on the panel (locked → ESP_ERR_NOT_ALLOWED, unlocked → live). The full story is in the lock/unlock closure box.

    The agent·

    ask <text>·

    Owner-scoped agent turn via POST /api/devices/ask → {text, card?} — the answer paints as a card. Since 0.15.0 the ask streams (STREAMING_UI.md): the request carries stream:"1", and a backend that knows the flag answers SSE — the words type onto the glass live (chat card: question = user bubble, answer types into the assistant bubble, caret at the tail, closing full refresh), and the relay reply text gains a [streamed to glass] suffix. A backend that ignores the flag gets the classic render-once path — the flag is an opt-in the server may decline. One ask at a time across all callers (button + relay share a single-flight mutex); a second concurrent ask is refused, never queued. This is the full agent, not a Q&A endpoint: tools, memory, cross-device reach — proven on glass with "what is my Mac mini's current disk usage?" answered from the wall (the turn ran use_device against another machine in the fleet). A 422 means nothing transcribed / empty speech; the firmware paints an honest "didn't catch that" card instead of pretending.

    voice [seconds] (default 5)·

    Same pipeline, but records the PDM mic first: WAV → /api/media → ask with audioUrl. This is exactly what the AI button does — the verb exists so the pipeline is testable remotely.

    Power & lifecycle·

    lock / unlock (since 0.17.0, grammar v5)·

    Pocket lockout — the P-1 safety pillar, manual half (IMU auto-entry is the next package). status carries the truth as "locked". While locked: physical touch is discarded at the router, AI press answers a double blip through the fabric and refuses, long-press home and UP/DOWN paging are dead, and the relay voice verb refuses — a remote-triggered pocket recording is the same privacy incident as an accidental one. The relay otherwise stays answerable by design: say/render_ui/screenshot/tap all work, because lockout guards the device's inputs, not the owner's reach (synthetic taps bypass the router gate on purpose). The unlock chord — UP+DOWN held 1 s — is read as raw GPIO by its own watcher task, deliberately independent of the button layer it gates: the one path back cannot be disabled by the thing it escapes. Unlock re-renders the last card; lockout is a state, not a page.

    §11 half 2 — IMU auto-entry (since 0.17.2): the pocket locks itself. tiny_orient's existing 1 Hz reader (no new sensor task) feeds a policy in tiny_lock: face-down ≥ 3 s (az < −0.60 g — glass to the fabric) locks immediately; walking ≥ 5 s (sustained |mag| swings > 0.18 g between 1 Hz samples) locks only if nothing touched the device for 30 s — so carrying it while using it never fights you. Touch and buttons reset the idle clock. Auto-entry also resolves the standing edge below: a pocket reboot boots unlocked, but a pocket re-locks itself within seconds of the walk resuming. Two P-3 kindnesses ride along: rotation classification sleeps while locked (no orientation math for a pocket), and the locked miccheck refusal now names the reason in words instead of an errno — verified on the panel (0.17.2, fw_commit 6b94f2cd): locked → "miccheck refused: device is pocket-locked (S11) — the mic stays dead until unlock", unlocked → live mic, same actor, seconds apart. The IMU entry paths themselves (face-down, walk) need a hand and a pocket — they are the standing manual-verification item, and the constants are declared tunable on-device.

    The miccheck hole — found on glass, fixed on glass (closed)

    Lifecycle of a P1, all within hours: the docs lane ran the D-UX5 probe on the live 0.17.0 panel and a locked device answered miccheck 2 with two seconds of room audio (rms 2188, 99% nonzero) — the gate was a verb-name check on voice, the audio entry point unguarded, exactly the failure D-UX5 pre-registered before the build. 0.17.1 moved the gate to tiny_audio_record_wav, the single funnel every capture path shares. Closed with a same-session A/B on the physical panel (0.17.1, fw_commit cbdca800): lock → miccheck 2 → record failed: ESP_ERR_NOT_ALLOWED; unlock → miccheck 2 → verdict:live, rms 2140. The refusal and the recovery, seconds apart, same device. Re-run on 0.17.2 after a P0 scare (a probe race made 0.17.1 look mic-leaking — third confirmed instance of the stale-envelope trap): refusal holds, and it now speaks human — "device is pocket-locked (S11) — the mic stays dead until unlock" — instead of an errno.

    Probe discipline note, learned the honest way: the first 0.17.1 probe returned live — because it rode a stale pending envelope executed after another lane's unlock. Verdicts only count when the lock and the probe are the same actor, seconds apart; a queued envelope proves nothing about the state it was aimed at (same class of trap as the "locked at boot" sighting, which was also a queued envelope).

    Boot truth, absorbed from 0.17.1's receipts: the device boots unlocked — so a pocket reboot (crash, brownout) silently exits lockout. Documented as the standing argument for §11's IMU auto-entry half, which would re-enter on its own.

    glance (since 0.18.0, grammar v6)·

    The pager lesson as a verb: redraw the cached current card through the partial-refresh path — no full-panel flash, no network, no re-composition — so the title-bar cluster (clock · battery · Wi-Fi · dmN unread when > 0 · [L] when locked) is current the moment the glass is looked at. Replies with a JSON receipt that names its refresh path, so the no-flash acceptance is in the reply, not in trust:

    {"refresh":"partial","battery_pct":100,"wifi":true,"unread":0,"locked":0}

    Verified on the panel the hour it shipped (0.18.0, fw_commit d64024a3): receipt above is a live reply, refresh:"partial" confirmed from an awake device. This is the relay half of §12 (glance-on-lift); the IMU wake half — lift the device, get this redraw unasked — rides the same tiny_display_glance() and is hand-verification territory, like the auto-lock entry paths.

    sleep [seconds]·

    Deep sleep. Order matters, and it's deliberate: reply first (the PATCH must land while the radio is up) → paint the goodbye card (e-ink keeps it at 0 mA — that is the magic) → hand over to the HAL, which holds the power latch and gates the wake pin. The AI button (EXT1, GPIO4) always wakes; optional seconds adds a timer wake so sleep is remotely testable.

    messages [unread | thread <login>] (since 0.14.7)·

    The DM rail, driven remotely. Bare messages puts the inbox card on the glass; messages thread <login> opens that conversation; messages unread answers the badge counts as JSON and renders nothing (a monitoring probe should not repaint a panel). All three fetch with the device's own token over /api/devices/messages — no owner-side process anywhere. Same paths as a finger: a tapped m: row and a pushed verb converge on one fetch-and-render.

    ota [channel] (default sticky-dev)·

    Stage from the channel pointer → sha256-verify → reply then reboot into a rollback-armed trial (after esp_restart nobody would hear the result). Replies already up to date (<fw version>) when current, OTA failed: <esp_err> otherwise. Since 0.14.9 the stage also refuses downgrades: ver_cmp parses MAJOR.MINOR.PATCH[-mN] numerically (0.2.0 < 0.14.8 — no lexicographic trap), an unparseable version is INCOMPARABLE, and incomparable-without-force = refuse, fail closed. The refusal reply is an actionable sentence, not an error code. A publisher who truly means to go backwards writes force:"1" into the bundle — and the forced install logs loudly.

    Not in the firmware (yet)·

    wake (a sleeping device can only be woken by button/timer — the radio is off), reprovision (the rescue portal opens itself after a 3-strike auth-halt — 0.14.12), press (no synthetic twin for buttons/long-press yet — tap and swipe cover the touchscreen but not the three physical keys), image/stream (planned; the qr card and render_ui cover most needs today). ~~lock/unlock~~ shipped in 0.17.0 and moved up to Power & lifecycle — the pre-registered probe (tools/probe_lockout.sh) did its job both ways: the build had a test to meet, and the test caught the one gate the build missed (miccheck, see the bug box there). The dashboard greys these out with the reason — an action that does nothing is a lie on the screen.

    Reply plumbing (all verbs)·

    Replies go PATCH /api/devices/relay with inReplyTo and a payload that is a JSON-serialized string ({"result":"…"}), capped at 8 KB; images ride as hosted URLs, never bytes. A single 401 never wipes identity (blips happen — the M9 lesson, learned when one transient 401 bricked a good token): three consecutive auth failures trip an auth-halt (auth_halted:true in status), and since 0.14.12 the halt raises a rescue portal — live STA widens to APSTA, the same /setup contract as first boot, so a re-issued token has a path onto the device without a serial cable. STA stays associated throughout, so a 401 that clears self-heals without the portal ever being used.
